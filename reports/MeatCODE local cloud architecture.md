# Keep MeatCODE Cloud-Served and Locally Guarded

**MeatCODE should adopt a hybrid architecture now: keep the authoritative scientific data and always-on product in managed cloud services, while keeping rights-sensitive PDFs, GROBID parsing, exact evidence passages, and restricted-text extraction inside a controlled local boundary.** This is not a compromise between two equal designs; it is the smallest architecture that preserves the working Neon-plus-Render product without sending publisher-controlled text into unapproved infrastructure. Neon should remain the only production system of record, Render should remain the stateless query/API server, and graph/vector systems should remain rebuildable projections rather than new authorities. Locality should be selected by rights and evidence sensitivity, not by a belief that local computing is automatically cheaper or secure; cloud placement should be selected by availability, team access, recovery, and measured scaling needs, not by a belief that managed services automatically make processing compliant. The 10-paper pilot should therefore run GROBID and restricted extraction locally, admit only checked derived facts and provenance into Neon dev, and benchmark local versus hosted models on identical evidence before any hardware purchase or provider commitment. The noon decision on **18 October 2026** should approve this boundary and the pilot—not a permanent LLM vendor, Neo4j, LightRAG, a GPU, or cloud storage for paid full text. Research and source status in this report are current through 18 October 2026.

## One cloud authority and one local evidence lane resolve the immediate decision

**Verified current state.** MeatCODE is not choosing from a blank sheet. Its production API is already a stateless Python service on Render, its production and development data already live in separate Neon Postgres branches, and the current Render Python service cannot run Docker ([MeatCODE systems map](../platform_docs/SYSTEMS_MAP.md)). The live retrieval baseline is Postgres full-text search over 818 sources; the platform has 798 non-junk molecules and 3,650 provenanced molecule-property observations, but only 23 paper-to-molecule links, no experiment/process rows, and no molecule-property observation that cites a paper ([current project state](../PROJECT_STATE.md); [RAG build-versus-buy memo](../platform_docs/RAG_BUILD_VS_BUY.md)). The existing knowledge graph is already a projection rebuilt from Neon rather than an independent database, and its blocker is bridge density between papers and molecules—not graph traversal technology ([knowledge-graph decision](../platform_docs/KG_DECISION.md)). These facts make an all-local redesign unnecessary and make a second authoritative graph store actively costly.

**Proposed decision.** Approve a hybrid v1 with a single authoritative cloud data plane and a controlled local evidence-processing plane. The serving flow is `user → Render API → Neon retrieval → hosted answer model → cited response`; the ingestion flow is `rights gate → controlled source vault → local GROBID → extraction/checking/validation → transactional Neon dev admission → evaluation → promotion`. Parsing, extraction, indexing, and graph construction must never occur synchronously inside a user request. Render itself separates request-serving web services from background workers and ETL-oriented workflows, which supports this operational split ([Render service types](https://render.com/docs/service-types)). The architecture also preserves the repository’s existing rule that publisher full text and raw passages stay out of Neon, GitHub, Render, public APIs, persistent vector stores, and graph stores until rights permit otherwise ([MeatCODE data-processing architecture](../platform_docs/DATA_PROCESSING_ARCHITECTURE.md)).

**Inference.** This is a hybrid execution design, not a hybrid source-of-truth design. Every admitted scientific claim, measurement, condition, identity, audit verdict, and source locator should resolve to Neon; Git remains authoritative for code, schema, prompts, controlled predicates, and decision records; PDFs and exact passages remain controlled evidence; TEI, chunks, embeddings, graph projections, summaries, and model outputs remain derived. A local or hosted model may propose a fact, but it cannot make that fact authoritative. The admission gate—independent checking, deterministic validation, and human review—must be identical regardless of where inference ran.

**Meeting-ready approval text.** “For the 10-paper pilot, MeatCODE will retain Neon as its only production scientific system of record and Render as its stateless always-on server. Rights-sensitive PDFs, TEI, and evidence extraction will stay in an encrypted local workspace; hosted models will receive only open, contractually approved, or admitted derived content. GROBID and ingestion will run asynchronously outside the web server. Graph and vector layers will be rebuildable projections from Neon. We will revisit cloud ingestion, dedicated local hardware, LightRAG, and Neo4j only after the rights decision and a measured pilot.”

## All-local and all-cloud each fail a different requirement

All three patterns are technically possible, but their product and governance consequences are not equivalent. **All-local maximizes direct control over raw inputs but would turn Lior’s machine, power, connectivity, patching, backups, and availability into production dependencies.** It would also migrate a working shared product away from Neon and Render, force the team to self-operate the database and inference infrastructure, and still would not create publisher text-and-data-mining rights. The EU research-mining exception depends on lawful access, purpose, jurisdiction, and security; local execution does not override a licence or an express reservation of mining rights ([Directive (EU) 2019/790, Articles 3–4](https://eur-lex.europa.eu/legal-content/EN/ALL/?uri=CELEX:32019L0790)).

**All-cloud simplifies shared operations but crosses the one boundary MeatCODE has not yet been authorized to cross:** uploading rights-limited full text and exact passages to cloud storage or model processors. Commercial API data is generally not used for training by default, but that is different from zero retention, no human access, no subprocessors, regional processing, or legal permission to upload. OpenAI documents default abuse-monitoring retention of up to 30 days and separate eligibility for Modified Abuse Monitoring or Zero Data Retention; its Files, Batch, and hosted Vector Store endpoints are not Zero Data Retention eligible ([OpenAI API data controls](https://developers.openai.com/api/docs/guides/your-data)). Anthropic likewise documents standard retention and separate Zero Data Retention arrangements, while Message Batches are not Zero Data Retention eligible ([Anthropic retention controls](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention)). An all-cloud pipeline is therefore appropriate only for open or explicitly approved content, not as the current default.

| Pattern | Strongest advantages | Decisive disadvantages for MeatCODE | Decision now |
|---|---|---|---|
| **All local** | Raw documents can remain on one controlled network; offline execution is possible; no per-token fee after hardware acquisition; easy experimentation | Makes a personal machine or self-managed server an availability and disaster-recovery dependency; adds database, security, patching, monitoring, and backup work; frontier-quality extraction may exceed unmeasured hardware; local processing does not create legal rights | **Reject as the target.** Keep local as the restricted ingestion lane. |
| **All cloud** | Shared availability; managed database/recovery; elastic inference; easier separation of web and workers; no GPU purchase | Publisher text leaves the controlled boundary; endpoint retention and regional controls require contract review; recurring vendor and egress cost; cloud credentials and services expand the attack surface; premature for a 10-paper pilot | **Reject for the MVP.** Permit only for open/licensed-and-approved inputs. |
| **Hybrid** | Preserves Neon and Render; isolates sensitive evidence; keeps the query product always on; allows identical local/hosted benchmarking; components can move independently | Requires explicit rights routing, two execution zones, versioned manifests, and tested recovery; local ingestion pauses when its approved worker is unavailable; careless implementation can create split-brain state | **Approve.** One Neon authority, one controlled local lane, and no dual writes. |

The hybrid design is operationally harder than pretending every input is equivalent, but that complexity corresponds to a real difference in legal and scientific risk. It can be controlled with a four-state rights router—**open, licensed and cloud-approved, internal/local-only pending rights, excluded**—before any parsing, embedding, or model call. Open and approved content may use regional managed services; pending content remains local; excluded content is metadata-only. This routing rule is more important than the brand of LLM or graph database.

## Ten component placements keep authority, workload, and rights aligned

The component decision below distinguishes **authority** from **execution**. A service may run locally or in the cloud without becoming authoritative; conversely, an authoritative record requires governed admission regardless of execution location.

|---|---|---|---|---|

Keeping one record avoids reconciliation and preserves transactional admission ([Neon branching](https://neon.com/docs/introduction/branching)). | Reconsider only after a documented compliance, availability, cost, or performance failure that Neon cannot meet. |
| **“Deducing” or extraction LLM** | **Portable router: local by default for restricted text; hosted only for open/licensed-and-approved text** | Outputs are candidates until checked and admitted | A local endpoint reduces third-party disclosure; a hosted frontier model can be used where rights permit and the benchmark shows a material quality gain. Move from laptop to institutional worker when availability or measured throughput misses the ingestion target. |
| **Interactive answer LLM** | **Hosted API called by Render through a provider-neutral adapter** | Never authoritative; receives only admitted, rights-permitted representations and must return source-linked synthesis | Interactive quality and elastic inference matter more than local control once restricted full text is excluded from context. | **Relevance-tier storage** | **Logical relevance/admission state in Neon; encrypted local vault for restricted artifacts; managed EU object storage later for permitted artifacts** | Neon keeps identity, rights, relevance, locator, hash, and retention class. If licences prohibit backup copies, preserve an auditable reacquisition manifest. |

The model layer must be split by role. **Extraction** binds molecules, values, conditions, and evidence; **query synthesis** turns admitted records into an answer; **checking/judging** independently detects unsupported or malformed outputs. They should not be assumed to need the same model. LightRAG’s own guidance treats graph extraction as more demanding than ordinary RAG and recommends a roughly 30B-class local extraction model, while a packaged quantized model of that class can occupy about 19–32 GB before runtime cache and context overhead ([LightRAG](https://github.com/HKUDS/LightRAG); [Ollama Qwen3 model sizes](https://ollama.com/library/qwen3/tags)). That makes a modern workstation plausible for a measured batch pilot, not proof that a laptop is a reliable production extractor. A schema-valid JSON result is also not scientific evidence: published biomedical and chemistry extraction results still show substantial error on complex relations, so deterministic checks and human admission remain mandatory ([Brokman et al., 2025](https://aclanthology.org/2025.wasp-main.6/); [GOSyBench proceedings](https://aclanthology.org/2024.langmol-1.pdf)).

## Four reversible stages move the existing system without a platform rewrite

The path should preserve the working service and change one risk boundary at a time. **Stage 0 is the verified system today:** Render serves the Oracle, Neon holds production/dev data, Postgres full-text search is the baseline, and the evidence bridge is sparse. The architecture record already defines the governed source-to-admission procedure and acceptance gates, but it is a recommendation awaiting team sign-off rather than an implemented pipeline ([MeatCODE data-processing architecture](../platform_docs/DATA_PROCESSING_ARCHITECTURE.md); [decision log](../platform_docs/DECISIONS.md)).

| Stage | What changes | What must be demonstrated before advancing |
|---|---|---|
| **1 — Approve boundary before noon** | Accept the hybrid architecture, one-authority rule, four-state rights router, and explicit local/cloud boundaries. Name owners for publisher rights, scientific adjudication, and backup policy. Freeze the 10-paper corpus and access class for each paper. | Written meeting decision; no ambiguity about whether protected text may enter hosted models or cloud storage; named reviewers and owners. |
| **2 — Run the 10-paper local pilot** | Vault PDFs locally; run GROBID; freeze stable evidence passages and manifests; run deterministic extraction plus one or more versioned local/hosted model configurations only where permitted; check every admitted record; write complete batches transactionally to Neon dev; build embeddings/graph only after admission. | Measured PDF/TEI sizes, parse failures, OCR rate, wall time, peak memory, model tokens/throughput, reviewer minutes, field-level precision/recall, severe-error count, and cost per accepted record. Pilot must preserve zero invented citations and meet the repository’s provenance and numeric-fidelity gates. |
| **3 — Harden the operational local lane** | If ingestion becomes recurrent, move from Lior’s laptop to a GFI-managed workstation or institutional Linux/GPU worker; add private-network access, service identities, encrypted storage, minimal-content logs, health checks, a second operator, and tested restoration. Keep the same manifest and model adapter. | Local model passes quality gates; backlog or machine availability misses the agreed cadence; owner, patching, incident response, RPO/RTO, and backup rights are approved. |
| **4 — Scale only approved workloads in cloud** | Provision versioned EU object storage and an ephemeral worker/workflow for open/licensed-approved artifacts; separate interactive and ingestion credentials, budgets, queues, and database pools. Keep restricted content in the local lane. | Written processing rights; provider/region/retention review; object lifecycle and key ownership; measured throughput need; one-way artifact lineage; restore and deletion tests. |

The batch worker should implement a visible state machine such as `registered → rights_checked → queued → parsing → parsed → extracting → validating → human_review → admitted_dev → evaluated → promoted_prod`, with explicit terminal states for quarantine, rights exclusion, retryable failure, and permanent failure. Work identity should include at least source ID, input hash, parser version, model/configuration, prompt version, and schema version. A retry with the same identity resumes; a changed component creates a new run. Admission is transactional, while embedding and graph projection occur afterward and can be rebuilt independently. This prevents both partial scientific writes and hidden model drift.

## Rights, review, and recovery dominate cost and operational risk

**Cost inference.** At the planned scale, raw model and embedding charges are unlikely to decide the architecture. Using the project’s rough 10–20 million extraction-input-token scenario and assuming structured output of 20% of input, current public list rates imply an illustrative one-pass cost of roughly **$2–$4 for a low-cost model configuration or $40–$80 for a higher-capability hosted configuration**, before prompts, retries, overlap, regional premiums, and a second checker; eligible batch pricing can halve token charges ([OpenAI pricing](https://developers.openai.com/api/docs/pricing); [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)). The same 10–20 million tokens cost roughly **$0.20–$0.40** with OpenAI’s small embedding model or **$1.30–$2.60** with its larger one at current list prices ([OpenAI embeddings](https://developers.openai.com/api/docs/guides/embeddings)). These numbers are planning arithmetic, not project quotes. **Human adjudication, repeated runs, unbounded retries, idle GPU capacity, duplicate infrastructure, security ownership, and recovery testing are likely to cost more than first-pass tokens.** The pilot should therefore report total cost and reviewer minutes per accepted scientific record, not merely API spend.

**Security inference.** “Local” must not be used as a synonym for secure or durable. The restricted lane needs full-disk or volume encryption, least-privilege access, loopback/private binding, disabled cloud features and restricted egress where required, pinned containers/models, minimal logs, versioned manifests, a named second operator, and tested recovery. LightRAG binds broadly by default and warns that endpoints are public without keys/accounts or loopback restriction; vLLM warns that its built-in API key does not protect every path and recommends hardening behind a reverse proxy ([LightRAG security guidance](https://github.com/HKUDS/LightRAG); [vLLM server security](https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/)). Conversely, “cloud” must not be used as a synonym for noncompliant: managed encryption and availability are valuable, but processing rights, data location, retention, subprocessors, credentials, deletion, and incident response still require explicit approval.

**Explicit non-decisions for the meeting.** The hybrid boundary does not select a permanent extraction model, answer model, embedding model, LLM provider, object-storage vendor, queue, or GPU. It does not approve production Neo4j or LightRAG; neither tool choice forces local or cloud deployment, and both remain evaluation candidates rather than authorities. It does not approve cloud storage or hosted inference for paid/publisher full text. It does not purchase hardware, introduce a separate vector database, or assume that a 10-paper manual process is the final ingestion platform. Deferring these choices is disciplined sequencing because each depends on evidence the project does not yet have.

| Open evidence required | Why the architecture cannot infer it | Decision it unlocks |
|---|---|---|
| **Publisher/licensing determination** for mining, local retention, quotation, cloud processing, and backups | Provider privacy terms do not grant publisher rights; local execution does not create lawful access | Whether paid text may enter any hosted model, cloud bucket, or off-device backup |
| **Exact 10-paper corpus and access classes** | Throughput and quality depend on journals, scans, tables, figures, and rights | Pilot execution and representative error measurement |
| **Gold annotations and named scientific reviewer** | No generic benchmark matches MeatCODE’s flavor/aroma ontology, condition binding, units, and provenance | Local-versus-hosted model selection and admission thresholds |
| **Mac/workstation hardware and measured runtime** | Model file size does not predict sustained tokens per second, thermals, concurrency, or reviewer cadence | Whether the laptop is sufficient, a managed workstation is needed, or a GPU purchase has a business case |
| **Verified database contracts for experiments/processes and batch lineage** | The pipeline cannot safely hide missing governed fields in opaque JSON | Whether a numbered migration is required before admission |
| **RTO, RPO, retention, encryption, deletion, and key ownership** | “Backed up” and “encrypted” are not testable outcomes without owners and targets | Backup provider, retention design, restore cadence, and local-vault continuity |
| **Interactive latency, ingestion cadence, concurrency, and monthly budget** | Autoscaling and queues solve measured workload problems, not abstract ones | When to add managed workers, disable database scale-to-zero, or separate quotas/pools |
| **Actual GFI provider configuration** for residency, retention, DPA/ZDR, subprocessors, and regional availability | Marketing defaults cannot substitute for organization-level settings and endpoint-specific behavior | Which hosted provider/configuration is eligible for which data class |

**Future triggers are deliberately concrete.** Hosted processing of restricted text requires written rights approval plus verified regional/retention controls and a passing benchmark. Cloud GROBID requires cleared inputs plus a real unattended-throughput need. A dedicated local GPU requires a local model that passes the gold set and a measured total-cost or mandatory-boundary advantage, with an operational owner. Neo4j requires recurring multi-hop/Cypher workflows that the Postgres projection cannot meet at an agreed service level. LightRAG requires an evaluation configuration that beats the current retrieval baseline without storing prohibited chunks or bypassing MeatCODE’s chemistry schema. A separate vector database requires pgvector to fail a measured recall/latency/throughput target after tuning. Each trigger makes the architecture reversible instead of speculative.

## Conclusion

The architecture question becomes much simpler once MeatCODE separates **where evidence may be processed** from **where accepted knowledge must live**. The correct near-term design is not “some data local and some data cloud” in an ad hoc sense; it is a governed local evidence lane feeding one managed cloud authority through a strict admission gate. That preserves the product’s current availability, prevents a new publisher-text exposure, and allows local and hosted models to compete on the same scientific benchmark rather than on preference or vendor claims.

The most important investment before noon is therefore a boundary decision and ownership, not infrastructure procurement. Once the 10-paper pilot measures quality, reviewer effort, throughput, and recovery needs, MeatCODE can move specific cleared workloads to managed workers or specific restricted workloads to a dedicated local machine without changing its scientific data model or creating a second truth.

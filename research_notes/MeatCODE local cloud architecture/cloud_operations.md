# Hosted cloud LLMs and managed infrastructure for MeatCODE

## Which stages benefit most from managed cloud services and autoscaling?

### Takeaway
MeatCODE should use a **hybrid architecture**, not choose “all local” or “all cloud.” Keep the public API, Neon system of record, approved object storage, backups, and interactive hosted-LLM calls in the cloud; keep rights-limited PDFs and GROBID processing local until publisher and provider-processing rights are explicit. Move GROBID to an ephemeral cloud batch worker only after those rights are approved and the 10-paper pilot measures its actual CPU, memory, runtime, and parse quality.

### Cited Findings
- The current project decision already makes Neon Postgres the only production system of record, keeps publisher full text out of Neon/Render/vector/graph stores, calls for local GROBID, and treats retrieval systems as replaceable projections rather than authorities. — [MeatCODE data-processing architecture](https://github.com/Bokipr0/meatCODE/blob/dev/platform_docs/DATA_PROCESSING_ARCHITECTURE.md)
- The deployed MeatCODE platform already uses Render for the API and Neon branches for production and development; the current Render Python service cannot itself run Docker, so GROBID cannot simply be added inside the existing API service. — [MeatCODE systems map](https://github.com/Bokipr0/meatCODE/blob/dev/platform_docs/SYSTEMS_MAP.md)
- Render separates interactive web services from background workers, cron jobs, and durable workflows; it specifically describes workflows as appropriate for ETL and on-demand background jobs. — [Render service types](https://render.com/docs/service-types)
- Render cron jobs cannot access persistent disks, are stopped after 12 hours, and are billed by active runtime with a $1 monthly minimum; longer work belongs in a workflow or background worker. — [Render cron jobs](https://render.com/docs/cronjobs)
- A Render persistent disk is attached to one service instance only, prevents horizontal scaling and zero-downtime deploys, and is unavailable to cron and one-off jobs; snapshots are daily and retained for at least seven days. — [Render persistent disks](https://render.com/docs/disks)
- GROBID's full image is about 8 GB and is more accurate for some reference/citation tasks but uses materially more memory and is ideally GPU-backed; the CRF-only image is about 500 MB and faster/lighter but gives up some accuracy. The project recommends 6–8 GB RAM for intensive parallel processing and 24–32 GB for full deep-learning inference on CPU at concurrency eight. — [GROBID Docker guidance](https://github.com/grobidOrg/grobid/blob/master/doc/Grobid-docker.md); [GROBID production guidance](https://github.com/grobidOrg/grobid/blob/master/doc/Frequently-asked-questions.md)
- GROBID is multithreaded and uses a bounded parser pool; when the pool is exhausted it can return `503`, so concurrency must be sized to CPU/GPU capacity instead of treated as unbounded serverless work. — [GROBID service documentation](https://github.com/grobidOrg/grobid/blob/master/doc/Grobid-service.md)
- Neon separates storage from compute, supports autoscaling and scale-to-zero, and recommends pooled connections; an idle compute normally suspends after five minutes and waking it adds a few hundred milliseconds, which can be avoided by disabling scale-to-zero at higher compute cost. — [Neon compute management](https://neon.com/docs/manage/computes)
- Render offers Frankfurt as a deployment region, but an existing Render service cannot be moved between regions; it must be recreated and migrated. Services in different regions cannot share Render private networking. — [Render regions](https://render.com/docs/regions)

### Inferences
- **Recommended v1 placement:** (1) Render web service for the interactive API; (2) Neon for admitted relational facts, provenance, audit state, and—if evaluated—`pgvector`; (3) a versioned EU object bucket for open/approved PDFs, TEI, batch manifests, validation reports, and database exports; (4) local encrypted storage for rights-limited PDFs and their passages; (5) local Docker GROBID for the pilot; (6) hosted LLM APIs only for content whose licence and provider terms permit that processing. This preserves the project’s existing governance boundary while using managed services where availability matters. — [MeatCODE architecture](https://github.com/Bokipr0/meatCODE/blob/dev/platform_docs/DATA_PROCESSING_ARCHITECTURE.md); [Render service types](https://render.com/docs/service-types)
- The interactive path should remain stateless and horizontally scalable: `user -> Render API -> Neon retrieval -> hosted LLM -> cited answer`. PDF parsing, extraction, checking, embeddings, graph projection, and admission should never run synchronously in that request path. Render itself recommends offloading resource-intensive operations to workflows or background workers. — [Render scaling](https://render.com/docs/scaling)
- Do **not** use a Render persistent disk as the scientific source vault or shared batch workspace. Its single-instance and no-cron/no-one-off-job constraints conflict with a resumable, portable pipeline. Use object storage plus immutable content hashes and a manifest; mount local encrypted storage only for papers that cannot legally enter cloud storage. — [Render persistent disks](https://render.com/docs/disks); [S3 Versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html)
- At roughly 1,000 PDFs, cloud autoscaling is most valuable for bursty LLM/embedding calls, scheduled metadata ingestion, and eventual parallel extraction—not for keeping a large GROBID host running continuously. The first pilot can finish on one controlled local machine; persistent managed compute becomes justified only if ingestion frequency, team access, recovery requirements, or local-machine availability make the laptop a bottleneck. — [GROBID production guidance](https://github.com/grobidOrg/grobid/blob/master/doc/Frequently-asked-questions.md); [Render workflows pricing](https://render.com/docs/workflows-limits)
- Do not add a separate managed graph database solely because the project uses “Graph-RAG.” Generate graph edges from admitted Neon rows and benchmark the projection first. This avoids a second authority and a second backup/security/operations surface. — [MeatCODE data-processing architecture](https://github.com/Bokipr0/meatCODE/blob/dev/platform_docs/DATA_PROCESSING_ARCHITECTURE.md)

### Gaps
- Daniel/legal must decide whether paid publisher PDFs may be retained in an EU cloud bucket and whether their text may be processed by OpenAI, Anthropic, AWS, Google, or another subprocessor.
- The current Neon and Render deployment regions, Neon plan/restore window, and whether EU-only processing is a contractual requirement were not confirmed in the repository snapshot.
- The 10-paper pilot must measure PDF sizes, GROBID wall time, peak RAM, parse failures, OCR rate, and TEI size before choosing a managed worker size.
- The required API latency target, concurrent users, ingestion cadence, recovery-time objective (RTO), recovery-point objective (RPO), and monthly budget are not yet specified.

## What are the hosted-model privacy, retention, residency, and vendor-risk tradeoffs?

### Takeaway
Hosted APIs are appropriate for approved content and the interactive answer model because they offer the strongest models without GPU operations, but “not used for training” does **not** mean “not retained.” MeatCODE needs an explicit processing class per document and must verify endpoint-specific retention: normal synchronous APIs can be ZDR-eligible, while provider batch and file/vector features often retain data and may be incompatible with ZDR.

### Cited Findings
- OpenAI says API business data is not used to train models by default unless the customer opts in. Default abuse-monitoring logs can retain customer content for up to 30 days; eligible customers may request Modified Abuse Monitoring or Zero Data Retention. — [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data); [OpenAI enterprise privacy](https://openai.com/enterprise-privacy/)
- OpenAI’s endpoint table says `/v1/responses` and `/v1/embeddings` are ZDR-eligible, but `/v1/batches`, `/v1/files`, and `/v1/vector_stores` are not; batch application state is retained until deletion. — [OpenAI endpoint retention table](https://developers.openai.com/api/docs/guides/your-data)
- OpenAI data residency is configured per project and requires eligibility through sales. EU storage and processing are supported for selected endpoints/models, including GPT-6.1 Sol, GPT-6 Sol, and GPT-6 Luna in Standard, Flex, and Batch; regional endpoints for eligible post-March-2026 models carry a 10% uplift. — [OpenAI data-residency controls](https://developers.openai.com/api/docs/guides/your-data); [OpenAI pricing](https://developers.openai.com/api/docs/pricing)
- Anthropic says commercial API inputs/outputs are not used for training by default. Standard API inputs/outputs are normally deleted within 30 days, subject to legal/usage-policy exceptions, and ZDR is available only by agreement. — [Anthropic training policy](https://privacy.anthropic.com/en/articles/7996868-is-my-data-used-for-model-training); [Anthropic retention policy](https://privacy.anthropic.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data)
- Anthropic’s ordinary Messages API and structured outputs are ZDR-eligible, but Message Batches are not; batch inputs and outputs are stored for up to 29 days and results remain available for 29 days unless deleted earlier. — [Anthropic API retention matrix](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention); [Anthropic batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing)
- Anthropic exposes Claude through its first-party API and partner platforms including Amazon Bedrock and Google Cloud. Regional or multi-region partner endpoints carry a 10% premium over global routing for recent model families. — [Anthropic pricing and cloud platforms](https://platform.claude.com/docs/en/about-claude/pricing); [Claude on Amazon Bedrock](https://docs.anthropic.com/en/api/claude-on-amazon-bedrock)
- Both model providers retire model versions. Anthropic states that publicly released models receive at least 60 days’ notice before retirement, while OpenAI publishes endpoint/model deprecation schedules. — [Anthropic model deprecations](https://docs.anthropic.com/en/docs/about-claude/model-deprecations); [OpenAI deprecations](https://developers.openai.com/api/docs/deprecations)

### Inferences
- Create four document-processing classes: **A open**, **B licensed and cloud-approved**, **C internal/local-only pending rights**, and **D excluded**. A/B may use approved regional hosted APIs; C must stay local and use a local model or deterministic methods; D is metadata-only. “API data is not trained on” is insufficient legal approval because default retention, batch storage, files, and subprocessors remain separate questions. — [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data); [Anthropic API retention](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention)
- For sensitive rights-limited text, use **synchronous, stateless Messages/Responses calls only if ZDR and rights approval are both in place**; do not use provider Batch, Files, or hosted vector stores. For Anthropic specifically, Message Batches are incompatible with ZDR. For OpenAI, `/v1/batches` is also explicitly not ZDR-eligible. — [Anthropic retention matrix](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention); [OpenAI endpoint retention table](https://developers.openai.com/api/docs/guides/your-data)
- Provider substitution requires an internal `ModelClient` boundary with a provider-neutral request/response contract, JSON schema validation, model/version/config recorded per extraction, and a fixed evaluation suite. Store prompts, schema versions, derived JSON, and embeddings in MeatCODE-controlled systems rather than provider files/vector stores. Model retirement then becomes a controlled migration, not a data migration. — [OpenAI endpoint retention table](https://developers.openai.com/api/docs/guides/your-data); [Anthropic model deprecations](https://docs.anthropic.com/en/docs/about-claude/model-deprecations)
- Keep at least two qualified provider configurations behind the same evaluation harness, but do not perform silent fallback on scientific extraction: a provider/model change must be written to the batch manifest and compared against the gold set. Interactive queries may retry a second provider after a visible transient failure only if citation and answer contracts are identical. — [OpenAI rate-limit guidance](https://developers.openai.com/api/docs/guides/rate-limits); [Anthropic model deprecations](https://docs.anthropic.com/en/docs/about-claude/model-deprecations)

### Gaps
- Neither provider’s general documentation resolves MeatCODE’s publisher licences; a provider DPA/ZDR setting cannot grant text-mining rights that the publisher licence withholds.
- Eligibility, contract terms, pricing commitments, subprocessor list, and actual EU-region availability must be confirmed for the exact GFI organization and chosen model snapshot before sending protected text.
- The scientific extraction benchmark—not provider marketing—must determine whether a low-cost hosted model, high-capability hosted model, or local model meets MeatCODE’s precision and provenance gates.

## How should batch ingestion and interactive query workloads be separated?

### Takeaway
Use two independently deployable workloads sharing only governed stores and schemas: a low-latency stateless query service and a resumable, idempotent batch pipeline. Batch jobs may wait hours and use discounted inference; the interactive Oracle must stream quickly, enforce small context budgets, and never wait for parsing, graph construction, or corpus-wide extraction.

### Cited Findings
- Anthropic Message Batches reduce input and output token prices by 50%, can take up to 24 hours, and keep results for 29 days. — [Anthropic batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing); [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- OpenAI lists separate Standard and Batch prices, with current Batch prices one-half of Standard for GPT-6 Astra, GPT-6.1 Sol, and GPT-6 Luna. — [OpenAI pricing](https://developers.openai.com/api/docs/pricing)
- OpenAI APIs can return `429 slow_down` during rapid traffic growth and `503 server_is_overloaded`; the official guidance is to follow `Retry-After`, back off with jitter, and distinguish transient overload from billing/quota errors. — [OpenAI rate limits](https://developers.openai.com/api/docs/guides/rate-limits)
- Render recommends workflows or background workers for resource-intensive work; cron runs have a single-run guarantee but are capped at 12 hours and cannot use persistent disks. — [Render scaling](https://render.com/docs/scaling); [Render cron jobs](https://render.com/docs/cronjobs)
- Render Workflows provide durable execution, automatic retries, and per-second active compute billing, with published configurations from usage-based `flex` through fixed CPU/RAM tiers. — [Render Workflows pricing](https://render.com/docs/workflows-limits)

### Inferences
- **Interactive service:** deploy the existing Oracle/API as a stateless Render web service in the same European region as practical; use pooled Neon connections; retrieve a small approved context; call one hosted model synchronously with streaming; set a request deadline and bounded retry; log provider request ID, model snapshot, latency, token counts, cited source IDs, and failure class. — [Neon compute management](https://neon.com/docs/manage/computes); [OpenAI latency guide](https://developers.openai.com/api/docs/guides/latency-optimization)
- **Batch pipeline:** represent each run by an immutable manifest and state machine (`queued -> parsing -> extracted -> checked -> validated -> admitted/failed`). Each stage writes content-addressed artifacts and can resume without redoing completed work. Admission to Neon occurs only after validation and in a transaction; model/API retries never write partial scientific records. — [MeatCODE data-processing architecture](https://github.com/Bokipr0/meatCODE/blob/dev/platform_docs/DATA_PROCESSING_ARCHITECTURE.md)
- **Cloud execution pattern after rights approval:** scheduler enqueues a batch; an ephemeral workflow downloads a permitted PDF from object storage, calls GROBID, uploads TEI and logs, then submits extraction/checking work. Do not make the continuously running API own this pipeline. For the pilot and rights-limited content, run the same container and manifest locally to prove portability. — [Render service types](https://render.com/docs/service-types); [GROBID Docker guidance](https://github.com/grobidOrg/grobid/blob/master/doc/Grobid-docker.md)
- Use provider Batch only for open or approved content where 24-hour latency and provider-side storage are acceptable. Use synchronous lower-volume calls for ZDR-sensitive content. This is a privacy/latency distinction, not merely a price optimization. — [Anthropic retention matrix](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention); [OpenAI endpoint retention table](https://developers.openai.com/api/docs/guides/your-data)
- Maintain separate rate limits, API keys/projects, budgets, queues, and observability dimensions for `interactive`, `ingest-extract`, `ingest-check`, `embeddings`, and `evaluation`. Batch surges must not consume the interactive user quota or exhaust the same database connection pool. — [OpenAI rate limits](https://developers.openai.com/api/docs/guides/rate-limits); [Anthropic Usage and Cost API](https://platform.claude.com/docs/en/manage-claude/usage-cost-api)

### Gaps
- Render Workflows’ fit for the exact GROBID image and RAM/GPU profile must be tested; the full GROBID image may justify a separate GPU-capable batch platform rather than Render.
- A queue technology, retry ceiling, dead-letter procedure, and job-state schema have not been selected.
- The team has not defined interactive p50/p95 latency, daily question volume, maximum batch completion time, or allowed provider fallback behavior.

## What cost drivers and failure modes matter at roughly 1,000 PDFs plus ongoing updates?

### Takeaway
At this corpus size, hosted embeddings and even one-pass hosted extraction can be inexpensive relative to engineering and scientific review. The dangerous costs are repeated LLM passes, oversized contexts, uncontrolled retries, always-on GROBID compute, duplicate artifacts/versions, human adjudication, and premature operation of multiple databases—not the raw storage of 1,000 PDFs.

### Cited Findings
- Current public OpenAI list prices are $0.10/$0.50 per million input/output tokens for GPT-6 Luna and $2/$10 for GPT-6.1 Sol; Batch halves those rates. — [OpenAI pricing](https://developers.openai.com/api/docs/pricing)
- Current public Anthropic list prices are $0.10/$0.50 per million input/output tokens for Claude Haiku 5.5 and $2/$10 for Claude Sonnet 5.5; Batch halves those rates. — [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- OpenAI lists `text-embedding-3-small` at $0.02 and `text-embedding-3-large` at $0.13 per million input tokens; default dimensions are 1,536 and 3,072, and the dimensions parameter can reduce stored vector size. — [OpenAI embeddings guide](https://developers.openai.com/api/docs/guides/embeddings); [embedding model pricing](https://developers.openai.com/api/docs/models/text-embedding-3-small)
- Render prices cron/workflow compute by active runtime, while ordinary scaled service instances are billed per instance; autoscaling a service therefore multiplies compute cost during scaled periods. — [Render pricing](https://render.com/pricing); [Render scaling](https://render.com/docs/scaling)
- S3 Versioning preserves prior objects but charges every version as a full object, not a diff; lifecycle rules are needed to control retained versions and cost. — [S3 Versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html)
- S3 encrypts all newly uploaded objects at rest by default; versioning, lifecycle transitions, and customer-managed keys can add recovery/control but also operational choices and charges. — [S3 encryption](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingEncryption.html); [S3 storage classes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/storage-class-intro.html)
- Neon can preserve up to 30 days of configurable history for point-in-time restore, with longer retention increasing storage usage. — [Neon point-in-time restore](https://neon.com/blog/announcing-point-in-time-restore)

### Inferences
- **Illustrative one-pass LLM scenario, not a quote:** if 1,000 PDFs yield 10–20 million extraction input tokens and structured output equals 20% of input, public list pricing implies approximately **$2–$4** for GPT-6 Luna or Claude Haiku 5.5, **$40–$80** for GPT-6.1 Sol or Claude Sonnet 5.5, and half those amounts in Batch. A second independent checker pass roughly doubles model cost before retries, chunk overlap, prompt tokens, and reprocessing. These are planning arithmetic from public rates, not a project quote. — [OpenAI pricing](https://developers.openai.com/api/docs/pricing); [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- **Illustrative embedding scenario:** the same 10–20 million input-token assumption is about **$0.20–$0.40** with `text-embedding-3-small` or **$1.30–$2.60** with `text-embedding-3-large`, before re-embedding and regional uplifts. Embedding cost is therefore unlikely to decide the local/cloud architecture; retrieval quality and data rights should. — [OpenAI embeddings guide](https://developers.openai.com/api/docs/guides/embeddings)
- First-pass budget controls should be: batch manifest token estimate; hard maximum chunks per paper; smaller model for schema-constrained extraction; stronger model only for low-confidence/disagreement cases; fixed retry ceiling; per-stage spend alerts; and no corpus-wide re-run without an evaluation-approved version change. — [OpenAI rate limits and spend controls](https://developers.openai.com/api/docs/guides/rate-limits); [Anthropic Usage and Cost API](https://platform.claude.com/docs/en/manage-claude/usage-cost-api)
- Primary failure modes and mitigations are: damaged/scanned PDFs -> quarantine/OCR; GROBID overload/OOM -> bounded concurrency and per-paper retry; provider 429/503 -> exponential backoff with jitter and dead-letter; provider batch expiry -> split smaller batches; invalid JSON or unsupported evidence -> schema failure and no admission; Neon connection exhaustion/cold wake -> pool/reconnect; cross-region latency -> co-locate API/database/object storage; accidental deletion -> database PITR plus independent object/database exports; provider model retirement -> pinned snapshots and benchmarked migration. — [GROBID FAQ](https://github.com/grobidOrg/grobid/blob/master/doc/Frequently-asked-questions.md); [OpenAI rate limits](https://developers.openai.com/api/docs/guides/rate-limits); [Anthropic batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing); [Neon compute management](https://neon.com/docs/manage/computes)
- Do not treat Neon PITR as the only backup. Keep periodic logical exports and batch manifests in a separate versioned object bucket, with a tested restore procedure and lifecycle policy. PITR protects a bounded time window; an independent export protects against project/account loss and long-lived corruption. — [Neon point-in-time restore](https://neon.com/blog/announcing-point-in-time-restore); [S3 Versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html)

### Gaps
- The 10–20 million input-token figure is a planning assumption from the project brief and must be replaced with measured GROBID/chunk/token counts from the 10-paper pilot.
- No estimate yet covers OCR, local electricity/hardware depreciation, cloud egress, regional premiums, human review hours, graph projection, repeated benchmarking, or storage of image/table derivatives.
- Current Neon and Render invoices, API discounts/credits, and GFI enterprise agreements were not available; public list prices may differ from actual contracted costs.
- Backup frequency, restore test cadence, object-retention period, and the number of noncurrent versions to retain require owner decisions.

## What deployment pattern best preserves portability, reliability, and observability?

### Takeaway
Use owned, open data formats and replaceable adapters: Docker/OCI for GROBID, Postgres plus optional `pgvector` for authoritative/queryable data, S3-compatible objects for artifacts, provider-neutral model interfaces, and OpenTelemetry-style traces. Managed cloud should host replaceable execution, not own the only copy of scientific inputs, prompts, vectors, or graph facts.

### Cited Findings
- Neon is standard Postgres and supports `pgvector`; Neon recommends pgvector rather than its discontinued `pg_embedding`, and pgvector supports approximate-nearest-neighbor indexing when sequential scans become expensive. — [Neon pgvector direction](https://neon.com/blog/sunset-pgembedding); [Neon vector-search guidance](https://neon.com/blog/optimizing-vector-search-performance-with-pgvector)
- Render Blueprints define services, workers, cron jobs, workflows, regions, scaling, commands, and environment configuration as code; Render also supports Docker images for non-native workloads. — [Render Blueprint specification](https://render.com/docs/blueprint-spec)
- Render can stream service logs over TLS/HTTPS and, on Pro or higher, stream CPU, memory, network, HTTP, disk, and datastore metrics in OpenTelemetry format. Cron and one-off jobs are not included in the metrics stream, so application-level job metrics remain necessary. — [Render log streams](https://render.com/docs/log-streams); [Render metrics streams](https://render.com/docs/metrics-streams)
- Anthropic supports OpenTelemetry traces for Messages API requests and tools, including token usage; its Usage and Cost API can group and reconcile usage and cost, though it is not available programmatically for Claude Platform on AWS. — [Anthropic OpenTelemetry](https://platform.claude.com/docs/en/manage-claude/opentelemetry); [Anthropic Usage and Cost API](https://platform.claude.com/docs/en/manage-claude/usage-cost-api)
- OpenAI exposes organization usage and cost endpoints that can group by project, API key, model, batch, and service tier; it recommends the Costs endpoint for invoice reconciliation. — [OpenAI Usage API](https://platform.openai.com/docs/api-reference/usage)

### Inferences
- Define a provider-neutral model contract such as `extract(evidence, schema, policy) -> validated_json + usage + provider_metadata` and `answer(question, retrieved_evidence) -> answer + citations + usage`. Provider SDK objects must not leak into domain tables. Persist `provider`, exact `model_snapshot`, prompt/schema hash, temperatures/reasoning settings, request ID, token counts, latency, and validation verdict. — [Anthropic OpenTelemetry](https://platform.claude.com/docs/en/manage-claude/opentelemetry); [OpenAI Usage API](https://platform.openai.com/docs/api-reference/usage)
- Store vectors in Neon/pgvector and graph facts as Neon-backed projections, not in provider-specific hosted vector stores. Store PDF/TEI/manifests in an S3-compatible object interface with content hashes and lifecycle rules. This keeps model, vector engine, object provider, and graph implementation independently replaceable. — [OpenAI endpoint retention table](https://developers.openai.com/api/docs/guides/your-data); [Neon pgvector direction](https://neon.com/blog/sunset-pgembedding); [S3 Versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html)
- Minimum observability record per paper should include timings and status for acquire, rights gate, parse, chunk, extract, check, validate, embed, project graph, and admit; model tokens/cost; retries; GROBID version/image; artifact hashes; record counts; and rejection reasons. Minimum interactive record should include retrieval IDs/scores, model/provider, time-to-first-token, total latency, token/cost, citation validation, and failure class—without logging protected passages. — [Render metrics streams](https://render.com/docs/metrics-streams); [Anthropic OpenTelemetry](https://platform.claude.com/docs/en/manage-claude/opentelemetry)
- Put API, database, and approved object storage in one European region where feasible. If the existing Render or Neon resources are elsewhere, migration is an explicit project because Render regions cannot be changed in place. Avoid casually splitting services across regions, which increases latency, egress, and weakens private-networking options. — [Render regions](https://render.com/docs/regions)
- Decision for the meeting: **approve a hybrid v1**—cloud API/Neon/object storage/hosted interactive LLM; local rights vault and GROBID; hosted batch LLM only for open or contractually approved text; one provider-neutral adapter; no extra graph database until benchmark; revisit managed GROBID after the 10-paper pilot. This is the smallest reversible architecture consistent with current MeatCODE governance and managed-service capabilities. — [MeatCODE architecture](https://github.com/Bokipr0/meatCODE/blob/dev/platform_docs/DATA_PROCESSING_ARCHITECTURE.md); [Render service types](https://render.com/docs/service-types)

### Gaps
- Confirm whether the team can provision an EU object bucket, KMS key, service identities, and a secrets manager under a GFI-owned cloud account rather than Lior’s personal account.
- Confirm whether the existing Neon project is in an EU region and whether its plan provides the required PITR/availability guarantees.
- Select the portability target: direct OpenAI/Anthropic APIs behind one adapter, or a single hyperscaler (Bedrock/Vertex/Foundry) for consolidated identity, billing, and residency. The latter may simplify governance but increases cloud-platform coupling.
- Define service-level objectives and alerts before production: API availability/latency, ingestion completion, maximum queue age, budget threshold, parse-error rate, extraction-validation failure rate, backup age, and restore-test result.

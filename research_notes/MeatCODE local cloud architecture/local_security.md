# Local/self-hosted LLM and document processing for MeatCODE

_Research current to 18 October 2026. Scope: the local/self-hosted side of the PDF → GROBID → extraction → embedding → retrieval pipeline. Recommendations are explicitly separated from documented capabilities._

## Which MeatCODE stages can realistically run locally for an initial 1,000-paper corpus and ongoing incremental ingestion?

### Takeaway

GROBID parsing, deterministic normalization, local embeddings, validation, and batch-manifest generation are realistic on a workstation for 1,000 papers. Local LLM extraction is also technically possible, but a trustworthy chemistry extractor is a materially heavier workload: the current LightRAG project recommends a roughly 30B-class local extraction model, so it should be treated as a measured batch service rather than an always-on laptop feature.

### Cited Findings

- GROBID's standard local deployment is Docker. Its official documentation calls the full image the best-accuracy option and the CRF-only image the lower-memory, higher-throughput option. The full image is about 8 GB, the CRF image about 500 MB; GROBID recommends at least 4 GB GPU memory for the full image and 4 GB container RAM for full-text processing, rising to 6–8 GB for intensive parallel batches. — [GROBID Docker documentation](https://github.com/grobidOrg/grobid/blob/master/doc/Grobid-docker.md)
- GROBID reports roughly 10.6 full-text PDFs per second on a 16-thread, 32 GB RAM CPU server with the CRF image and tuned concurrency. This is an upstream-reported production example, not a guarantee for MeatCODE's PDFs, but it establishes that 1,000 PDFs is a small parsing batch on suitable CPU hardware. — [GROBID production configuration FAQ](https://github.com/grobidOrg/grobid/blob/master/doc/Frequently-asked-questions.md)
- The GROBID full image's deep-learning models improve bibliographic-reference parsing by 2–4 F1 points and citation-context identification by 2–5 points relative to the CRF-only image. Some additional DL configurations improve less while slowing overall processing by 2–3×. — [GROBID Docker documentation](https://github.com/grobidOrg/grobid/blob/master/doc/Grobid-docker.md)
- GROBID's published full Docker image is AMD64-first. On Apple Silicon/macOS it may run under emulation and therefore more slowly; Docker GPU acceleration for that image is supported only on Linux, not macOS. The CRF image has an ARM64 route documented and is the practical Mac default for a pilot. — [GROBID Docker documentation](https://github.com/grobidOrg/grobid/blob/master/doc/Grobid-docker.md)
- BGE-M3 is a 569M-parameter, 2.27 GB embedding model that supports dense, lexical and multi-vector representations, more than 100 languages, and inputs up to 8,192 tokens. Its modest model size makes workstation embedding realistic, although actual throughput still depends on chunk length, batch size and device. — [BGE-M3 official documentation](https://github.com/FlagOpen/FlagEmbedding/blob/master/docs/source/bge/bge_m3.rst)
- LightRAG provides an offline installation path, local storage backends, and Ollama integration. Its current guidance recommends BGE-M3 for local embeddings and a Qwen3-30B-A3B-Instruct-class model as a reasonable minimum for local entity/relation extraction because graph extraction is more demanding than ordinary RAG. — [LightRAG official README](https://github.com/HKUDS/LightRAG)
- LightRAG warns that an embedding model must be chosen before indexing and reused for query-time retrieval. Changing the embedding model requires re-embedding chunks, entities and relationships, and some storage backends require recreating vector tables. — [LightRAG official README](https://github.com/HKUDS/LightRAG)
- Ollama's packaged Qwen3-30B-A3B Q4 model is approximately 19 GB, Q8 approximately 32 GB and FP16 approximately 61 GB before runtime context/cache overhead. Ollama states that RAM/VRAM requirements rise with context length and parallel requests. — [Ollama Qwen3 model registry](https://ollama.com/library/qwen3/tags); [Ollama FAQ](https://docs.ollama.com/faq)
- Ollama runs natively on macOS and binds to `127.0.0.1:11434` by default. Its Docker GPU acceleration is unavailable on Docker Desktop for macOS, so an Apple Silicon workstation should use native Ollama/MLX-style inference rather than expecting Linux-container GPU behavior. — [Ollama FAQ](https://docs.ollama.com/faq); [Ollama macOS documentation](https://docs.ollama.com/macos)
- vLLM is designed for higher-throughput serving and provides OpenAI-compatible chat, response, embedding and other APIs. Its normal production target is Linux accelerator infrastructure; recent documentation also lists an Apple Silicon path through vLLM-Metal, but the Linux/NVIDIA path remains the conventional self-hosted server choice. — [vLLM quick start](https://docs.vllm.ai/en/v0.32.0/getting_started/quickstart/); [vLLM OpenAI-compatible server](https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/)

### Inferences

- **Recommended v1 boundary:** run rights classification, PDF vaulting, GROBID, passage segmentation, deterministic quantity/unit parsing, local embedding, evidence checking and batch packaging locally; write only approved derived records and source locators to Neon. This implements the current MeatCODE design without making the laptop the production database. — [MeatCODE architecture record](../../platform_docs/DATA_PROCESSING_ARCHITECTURE.md)
- **For the 10-paper pilot:** use GROBID CRF on the Mac first because it avoids AMD64 full-image emulation and is operationally simple. Compare a sample against the full GROBID image on Linux/GPU only if reference, citation-context or structure quality is insufficient. The decision should be based on MeatCODE's own table/caption/reference error rate, not GROBID's aggregate benchmark. — [GROBID Docker documentation](https://github.com/grobidOrg/grobid/blob/master/doc/Grobid-docker.md)
- **For 1,000 papers:** parsing and embeddings fit a normal modern workstation; LLM extraction is the capacity risk. Freeze chunks and manifests, then run extraction incrementally in resumable batches. Do not couple re-running GROBID to every LLM experiment.
- **Mac/workstation role:** best for the 10-paper pilot, incremental ingestion, investigator review and offline processing. A 30B Q4 model file alone is about 19 GB, so 32 GB unified memory is a bare planning floor and 64 GB offers safer headroom for the model, context cache, GROBID, embedding and OS; this is a capacity-planning inference, not a vendor guarantee. — [Ollama Qwen3 model registry](https://ollama.com/library/qwen3/tags); [Ollama concurrency guidance](https://docs.ollama.com/faq)
- **Dedicated on-prem Linux GPU role:** best when regular ingestion, several workers, or a shared internal endpoint is needed. A single 48 GB-class GPU is a sensible evaluation target for a 30B quantized extractor with context/cache headroom, while higher concurrency may require multiple GPUs; benchmark the actual prompt/context before purchase. This is a planning recommendation derived from the 19–32 GB packaged model sizes and Ollama's context/concurrency memory scaling, not a measured MeatCODE requirement. — [Ollama Qwen3 model registry](https://ollama.com/library/qwen3/tags); [Ollama FAQ](https://docs.ollama.com/faq)
- **Serving choice:** use Ollama for a single operator/workstation and vLLM for a dedicated Linux GPU service where batching and concurrency matter. Keep the extraction client behind a provider-neutral interface so the same gold benchmark can test local and hosted models.
- **Air-gapped role:** reserve for material whose licence or governance explicitly forbids any networked processing. Pre-download Python packages, container images, model weights, tokenizer caches and spaCy/tiktoken assets; LightRAG documents these otherwise easy-to-miss offline dependencies. Citation consolidation through Crossref is not offline; disable it or deploy a local consolidation service. — [LightRAG offline deployment guide](https://github.com/HKUDS/LightRAG/blob/main/docs/OfflineDeployment.md); [GROBID production FAQ](https://github.com/grobidOrg/grobid/blob/master/doc/Frequently-asked-questions.md)

### Gaps

- The Mac's exact chip, unified-memory capacity, free disk space and sustained thermal performance were not provided; no responsible throughput promise can be made without them.
- MeatCODE has not measured pages/PDF, scanned-page share, table complexity, total evidence-chunk tokens, or local tokens/second for the chosen extraction prompt.
- A 10-paper timed pilot is needed to measure parsing failure rate, extraction tokens, wall time, peak memory, energy/heat, and reviewer minutes per accepted record.
- The final local model, quantization, context size and inference server have not been selected. Hardware procurement should follow, not precede, that benchmark.

## When does publisher/licensing or data-governance risk make local execution the default?

### Takeaway

Local execution should be the default whenever the team cannot affirmatively show that a paper's access terms and the organization's policy allow its full text to be disclosed to the selected cloud processor. Locality reduces third-party disclosure, but it does not create text-and-data-mining rights, override a licence, or make retention automatically lawful.

### Cited Findings

- The EU Digital Single Market Directive's scientific-research TDM exception applies to research organisations and cultural-heritage institutions for works to which they have lawful access. It requires copies to be stored with an appropriate level of security and permits retention for research verification. The broader Article 4 exception is conditional on rightholders not having expressly reserved TDM rights. Applicability to MeatCODE, its jurisdictions and its contracts requires legal review. — [Directive (EU) 2019/790, Articles 3–4](https://eur-lex.europa.eu/legal-content/EN/ALL/?uri=CELEX:32019L0790)
- The same directive explains that lawful access may arise from open access, subscription/contractual arrangements or other lawful means, and contemplates access controls such as IP validation or user authentication for retained research copies. It does not say that running software locally cures a lack of lawful access. — [Directive (EU) 2019/790, recitals 14–15](https://eur-lex.europa.eu/legal-content/EN/ALL/?uri=CELEX:32019L0790)
- A hosted API is not necessarily used for model training: OpenAI states that API business data is not used for training by default, that ordinary API inputs/outputs are removed after 30 days unless legally required, and that eligible organisations can request Zero Data Retention. Those are material controls, but they remain third-party processing and must match the specific endpoint and organisation configuration. — [OpenAI enterprise privacy](https://openai.com/enterprise-privacy/); [OpenAI organisation data-retention API](https://developers.openai.com/api/reference/resources/admin/subresources/organization/subresources/data_retention/methods/retrieve)
- Ollama states that locally executed prompts and responses are not sent to Ollama; it also provides a local-only mode that disables cloud models and web search. Local-only mode must be set explicitly if the installation is signed in or cloud features are otherwise available. — [Ollama FAQ](https://docs.ollama.com/faq)

### Inferences

- Use a four-state rights gate before full-text processing: **open**, **licensed/approved for mining**, **internal-only pending decision**, and **excluded**. Only the first two should be eligible for a hosted LLM, and only after the provider, region, retention mode, subprocessors and output-storage policy are approved. — [MeatCODE architecture record](../../platform_docs/DATA_PROCESSING_ARCHITECTURE.md)
- Treat a hosted provider's “not used for training” statement as different from **zero retention**, **no human access**, **no subprocessors**, and **legal permission to upload**. Each is a separate control question. — [OpenAI enterprise privacy](https://openai.com/enterprise-privacy/)
- For rights-limited material pending Daniel/legal's decision, keep PDF, TEI and exact evidence passages in an encrypted local controlled workspace; send neither the full text nor persistent chunks to LightRAG, a hosted model, a graph store, Render, GitHub or Neon. Admit only checked derived facts, confidence and source locators to Neon. — [MeatCODE architecture record](../../platform_docs/DATA_PROCESSING_ARCHITECTURE.md)
- Local processing is the **risk-minimising default**, not the legal conclusion. Legal must still decide whether the source may be mined, how long local copies may be retained, who may access them, whether backups are permitted, and what excerpts/derived representations may leave the vault.
- A private cloud GPU or enterprise API can become acceptable when the contract explicitly permits processing and the deployment has approved region, retention, encryption, access logging, deletion and incident-response controls. Until then, “cloud but not training” is not equivalent to “approved.”

### Gaps

- The exact publisher licences, institutional subscriptions, governing jurisdictions and TDM reservations for the 1,000 papers were not available.
- No approved GFI policy was found for retaining publisher PDFs/TEI locally, backing them up off-device, using cloud processors, or retaining exact passages for scientific verification.
- It is unknown whether MeatCODE/GFI qualifies as a “research organisation” for each relevant national implementation of the EU directive; this is a legal determination, not an architecture assumption.
- The configured retention status of any current OpenAI/Anthropic organisation was not inspected. Marketing defaults must not be substituted for account-level evidence.

## What are the practical limits of local models for scientific extraction and evidence-grounded reasoning?

### Takeaway

Local models can perform structured extraction, especially after task-specific fine-tuning, but neither “open” nor “30B” guarantees scientific fidelity. Complex passages containing several entities, conditions and predicates remain difficult, and a schema-valid JSON result can still be scientifically wrong; MeatCODE therefore needs a gold benchmark, deterministic checks and human admission review regardless of hosting mode.

### Cited Findings

- LightRAG's current model-selection guidance says graph-RAG has higher model requirements than ordinary RAG because entity/relation extraction runs on every chunk and query generation must handle long, noisy retrieved context. It recommends a Qwen3-30B-A3B-Instruct-class model as a reasonable minimum for local extraction and a stronger model for final query answering. — [LightRAG official README](https://github.com/HKUDS/LightRAG)
- A 2025 biomedical relation-extraction benchmark covering seven datasets found zero-shot LLM performance approaching supervised methods on some datasets but still struggling with complex inputs that express multiple relations with different predicates. The evaluated models included GPT-4, o1 and the open-weight GPT-OSS-120B, so the difficulty is not confined to small local models. — [ACL Anthology: Brokman et al. 2025](https://aclanthology.org/2025.wasp-main.6/)
- A peer-reviewed chemical text-mining study evaluated compound recognition, reaction roles, MOF synthesis extraction, NMR extraction and reaction-action conversion. Fine-tuned GPT models reached 69–95% exact accuracy across those tasks, while fine-tuned Mistral and Llama 3 were reported as competitive. The task-specific result supports fine-tuning but does not establish accuracy on flavor/aroma claims, condition binding or MeatCODE's schema. — [Chemical Science / PubMed](https://pubmed.ncbi.nlm.nih.gov/38994403/)
- The GOSyBench chemistry KG-extraction work compared GPT-4, Claude, Mistral and GPT-4o approaches; its best system reached 73% recovery accuracy and 59% precision, explicitly leaving substantial room for improvement. — [ACL Language + Molecules 2024 proceedings](https://aclanthology.org/2024.langmol-1.pdf)
- Structured-output constraints improve format compliance but do not guarantee semantic truth. vLLM supports JSON-schema/regex/grammar-constrained output, while recent structured-extraction benchmarking reports that prompting strategy can improve structural validity yet increase semantic errors. — [vLLM structured outputs](https://docs.vllm.ai/en/v0.13.0/examples/online_serving/structured_outputs/); [LLMStructBench](https://arxiv.org/abs/2602.14743)
- Ollama states that Q4 KV-cache quantisation can reduce cache memory to roughly one quarter of F16 but with a small-to-medium precision loss that may become more noticeable at high context lengths; the quality impact is model- and task-dependent. — [Ollama FAQ](https://docs.ollama.com/faq)

### Inferences

- Do not select a local model from generic chatbot rankings. Evaluate extraction separately for: molecule identity, predicate/polarity, value/unit, matrix, temperature/time/pH/water activity, method, uncertainty, source locator, abstention and exact evidence entailment.
- Use the LLM only for semantic binding and classification. Use deterministic parsers for DOI/InChIKey/CAS candidates, literal number-and-unit checks, conversions, schema validation, duplicates and foreign keys. A valid JSON response is merely parseable, not admissible evidence. — [vLLM structured outputs](https://docs.vllm.ai/en/v0.13.0/examples/online_serving/structured_outputs/); [LLMStructBench](https://arxiv.org/abs/2602.14743)
- A small 7B–14B local model may be useful for triage, keywording or candidate generation, but should not be promoted to the production scientific extractor unless it beats the fixed acceptance gates on MeatCODE's annotated corpus. LightRAG's own 30B recommendation and the published relation-extraction error rates make “small model by default” an unsupported shortcut. — [LightRAG official README](https://github.com/HKUDS/LightRAG); [ACL Anthology: Brokman et al. 2025](https://aclanthology.org/2025.wasp-main.6/)
- The likely quality-maximising hybrid is: local model for rights-limited candidate extraction; frontier hosted model for open/approved content or as a checker; deterministic validator; then human scientific admission. The benchmark must compare identical passages, schema, prompts, decoding settings and gold labels, and report field-level precision/recall plus severe-error counts—not just aggregate answer preference.
- Quantisation and context settings are part of the model identity. Record exact weights, quantisation, runtime, context size and decoding parameters in every batch because changing them can change extraction quality even when the marketing model name is unchanged. — [Ollama FAQ](https://docs.ollama.com/faq)
- Do not ask any model—local or hosted—to “deduce” missing experimental values into the evidence layer. Unsupported values must remain null; an inference may be shown separately to users only if explicitly labelled as a hypothesis.

### Gaps

- No published benchmark exactly matches MeatCODE's flavor/aroma ontology, numeric-condition binding, tables and source-provenance contract.
- The team does not yet have a representative, adjudicated gold set. Without it, no claim that a local model is “good enough” or a cloud model is “better” is evidence-based.
- Local inference throughput for the chosen model, context and hardware remains unmeasured. Model file size does not predict acceptable batch latency by itself.
- The effect of GROBID parsing errors on downstream entity/relation extraction has not been measured on MeatCODE's journals, tables, figures and scanned documents.

## What controls are needed so “local” is not mistaken for secure or durable?

### Takeaway

A laptop-only pipeline is neither a security boundary nor a disaster-recovery plan. Local processing is acceptable only with encrypted storage, named access, loopback/private-network binding, restricted egress, patched and pinned software, minimal content logs, versioned manifests, multiple encrypted backups where licences permit, and tested restoration; the production service and approved facts should remain on managed, backed-up infrastructure.

### Cited Findings

- Ollama binds to loopback by default, but an operator can expose it by changing `OLLAMA_HOST`. Its local-only mode must be explicitly enabled to disable cloud models and web search. — [Ollama FAQ](https://docs.ollama.com/faq)
- LightRAG's server binds to `0.0.0.0` by default. Its README warns that, without API keys/accounts or loopback binding, every endpoint is public; even its Ollama-compatible routes remain open unless whitelist settings are changed. — [LightRAG official README](https://github.com/HKUDS/LightRAG)
- vLLM warns that its `--api-key` protects only selected path prefixes; other endpoints on the same HTTP server can remain unauthenticated, so its documentation recommends hardening behind a reverse proxy rather than relying on the built-in key alone. — [vLLM OpenAI-compatible server](https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/)
- GROBID writes temporary files under its configured temp directory and writes service logs. Its native PDF parser can fail on damaged/oversized/no-text PDFs, and GROBID recommends resource limits and concurrency tuning. These paths and failure artifacts are part of the sensitive-data boundary. — [GROBID configuration](https://github.com/grobidOrg/grobid/blob/master/doc/Configuration.md); [GROBID FAQ](https://github.com/grobidOrg/grobid/blob/master/doc/Frequently-asked-questions.md)
- NIST backup guidance recommends regular backups integrated with change management, testing and recovery exercises. NIST also describes a “backup-in-depth” approach with local, facility and disaster layers, and requires confidentiality, integrity and availability protections for backup information. — [NIST SP 1339](https://csrc.nist.gov/pubs/sp/1339/final); [NIST SP 800-82r3](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-82r3.pdf)
- NIST's data-confidentiality practice guidance treats access control, encryption and detect/respond/recover capabilities as complementary safeguards rather than assuming physical locality protects data. — [NIST SP 1800-28](https://www.nccoe.nist.gov/publication/1800-28/index.html); [NIST SP 1800-29](https://www.nccoe.nist.gov/projects/building-blocks/data-confidentiality-detect-respond-recover)

### Inferences

- **Storage boundary:** keep rights-limited PDFs, TEI, extracted images and exact passages in a dedicated encrypted vault outside Git, iCloud/consumer sync, Render, Neon and public APIs. Separate this vault from the working repository and from model caches. Store only pointers/hashes in batch manifests.
- **Access boundary:** use a named OS account, full-disk encryption, automatic screen lock, least-privilege file permissions and no shared credentials. A dedicated on-prem server needs SSH keys/MFA through the organisation's access layer, firewall rules and a separate service account.
- **Network boundary:** bind GROBID/Ollama/LightRAG/vLLM to loopback for a one-user workstation. For a shared server, place inference behind an authenticated TLS reverse proxy on a private network; do not expose raw inference ports to the Internet. Disable Ollama cloud features and deny outbound network access for an air-gapped or rights-limited worker. — [Ollama FAQ](https://docs.ollama.com/faq); [LightRAG README](https://github.com/HKUDS/LightRAG); [vLLM server security warning](https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/)
- **Logging boundary:** default to hashes, source IDs, batch IDs, timings and error codes. Do not log prompt bodies, full passages, model responses containing exact publisher text, PDF filenames that reveal restricted projects, or authentication secrets. Rotate and delete logs under an approved retention schedule.
- **Reproducibility boundary:** pin and record the GROBID version, container digest, model-weight hash, quantisation, embedding model/dimension, inference runtime, prompt/schema version, deterministic-parser version, source hash, batch manifest and validation output. Preserve rejected/corrected/admitted states separately.
- **Backup boundary:** Neon backups cover approved derived facts, not the controlled source vault. Where licences allow, maintain at least one separate encrypted backup of the vault plus manifests, with keys stored separately; where backup copies are forbidden, document that limitation and retain a reproducible reacquisition manifest. Test restoration on a schedule instead of assuming copied files are recoverable. — [NIST SP 1339](https://csrc.nist.gov/pubs/sp/1339/final); [NIST SP 800-82r3](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-82r3.pdf)
- **Availability boundary:** do not make Lior's Mac an always-on production dependency. The laptop is an ingestion worker; the hosted application, approved Neon facts and published retrieval service need team-owned credentials, documented recovery, health monitoring and a second authorised operator.
- **Patch/supply-chain boundary:** pin signed/reviewed container images and model artefacts, scan them before import, keep an inventory, and schedule controlled upgrades. An air gap reduces remote access but increases the risk of stale vulnerable software and makes update provenance more important.
- **Incident boundary:** define what happens after loss/theft, malware, accidental publication, corrupted extraction or key loss: revoke credentials, isolate the host, identify affected source batches, restore from tested backups, suppress affected derived records from retrieval and retain an audit trail.

### Gaps

- No approved retention/deletion periods, encryption-key owner, secondary operator, recovery-time objective or recovery-point objective were found for the local publisher-content vault.
- It is unknown whether the current Mac has full-disk encryption, managed endpoint detection, organisational backup, remote wipe or a separate work account enabled.
- The licences may permit local research copies but forbid off-site backup; that must be resolved per source class before implementing a backup policy.
- No tested runbook currently proves that the team can rebuild GROBID/model environments and restore batch manifests after loss of Lior's machine.
